# 루프마이너 개선 후보 — 2026-08-12 실측

기존 [루프마이너 분석](loop-miner.md)을 오늘 실제로 돌려서 현재 상태를 측정한 결과입니다.
**모든 항목은 실행 출력이나 파일 위치로 확인된 것이며, 추측은 없습니다.**

측정 명령: `pnpm run loop:tick`, `data/` 실측, `.github/workflows` 확인.

## 한눈에

| # | 개선 후보 | 가치 | 난이도 | 상태 |
|---|---|---|---|---|
| 1 | 검색갭 → 재수집 자동화 | **높음** | 낮음 | 유일하게 열린 고리 |
| 2 | `needs-glass.flag` 소비자 없음 | 중간 | 외부 의존 | **하루 넘게 방치됨** |
| 3 | 플래너 평가 케이스 0건 | 중간 | 낮음 | 케이스 축적 선행 |
| 4 | RAG 인덱스에 임베딩 모델 미기록 | 낮음 | 낮음 | 지금은 동작 |
| 5 | 제품 스크린샷에 장비 구분 없음 | 낮음~중간 | 낮음 | 오늘 추가분과 불일치 |
| 6 | 경계 게이트가 CI에 명시 단계 아님 | 낮음 | 낮음 | 간접 통과 중 |

---

## 1. 검색갭 → 재수집 (가장 가치 높음)

**실측**: `pnpm run loop:tick` 출력

```
"edge": "e2-queries-to-learn", "outcome": "manual",
"detail": "manual edge — engine never fires it"
```

**지금 실제로 놓치고 있는 것**이 파일에 남아 있습니다 (`data/feedback/search-gaps.jsonl`):

```json
{"query":"SCP 볼륨 서비스 503 장애 복구 절차","product":"HCI_SCP","hitCount":0,"reason":"no_hits"}
```

시스템이 **자기가 무엇을 모르는지 이미 알고 있는데**, 그걸 수집 대상으로 넘기는 연결이 없어서
그대로 쌓이기만 합니다. 이 한 칸만 이으면 지식베이스가 스스로 넓어지는 고리가 완성됩니다.

기존 루프마이너도 이걸 1순위 후보(난이도 낮음)로 지목했고, 오늘 실측으로 여전히 열려 있음이
확인됐습니다. 다른 세 에지(`e1`, `e3`, `e4`)는 엔진이 이미 자동으로 돕니다.

## 2. `needs-glass.flag` — 아무도 안 읽는 실패 신호

**실측**: `data/runtime/needs-glass.flag`

```
2026-08-11_03-00-05 glass_cdp_unreachable
```

KB 전체 재크롤이 **8월 11일 새벽부터 멈춰 있습니다.** 실패했다는 표시는 남겼는데 그걸 읽고
재시도하거나 알려주는 쪽이 없어서, 조용히 죽은 상태입니다.

최소 조치는 자동 복구가 아니라 **가시화**입니다 — 이 플래그가 살아 있으면 상태 조회에 드러나게
하는 것만으로도 "왜 최신 자료가 안 들어오지"를 며칠 뒤에 발견하는 일을 막습니다.

## 3. 플래너 평가 케이스 0건

**실측**: `data/evals/eval-cases.jsonl` 파일 없음.

평가 회귀 루프는 코드가 있어도 **비교할 기준 케이스가 없어서** 돌 수 없습니다.
첫 케이스는 새로 만들 필요도 없습니다 — 위 1번의 검색갭과 그에 대해 실제로 준 답을 짝지으면
그대로 회귀 케이스가 됩니다. 즉 1번을 하면 3번의 재료가 자동으로 생깁니다.

## 4. RAG 인덱스에 임베딩 모델이 최상위에 없음

**실측**:

```
version 2  chunks 1249  embeddingModel (미기록)
```

드리프트 검사는 오늘 정상 동작했습니다(`e3-drift-check: executed, no drift`). 다만 청크마다
기록된 모델을 읽어서 비교하는 방식이라, 부분 재임베딩으로 청크별 모델이 섞이면 판단 기준이
모호해집니다. 인덱스 최상위에 모델명을 한 번 기록해두면 명확해집니다.

## 5. 제품 스크린샷에는 장비 구분이 없음

**실측**: `packages/sangfor-screenshot/src/index.ts` 에 `deviceId` 없음.

오늘 `sangfor_console_capture_evidence`(콘솔 증거 캡처)에는 고객사/장비/날짜 구분을 넣었지만,
`sangfor_capture_screenshots`(제품 화면 일괄 캡처)에는 장비 구분이 없습니다. 같은 고객사에
같은 제품이 2대면 제품 스크린샷은 여전히 섞입니다. 동일한 방식으로 맞추면 일관됩니다.

## 6. 경계 게이트가 CI의 명시 단계가 아님

**실측**: `.github/workflows/ci.yml` 은 `lint / test / build / smoke:mcp / check:mcp-scorecard`,
`pr-validation.yml` 은 `lint / test / build / check:hygiene` 를 실행합니다.

`check:browser-boundary` 와 `check:data-scope-boundary` 는 **명시 단계가 아니고**,
`pnpm test` 안의 테스트가 그 스크립트를 실행하기 때문에 간접적으로만 통과합니다.
지금은 문제 없지만, 누군가 그 테스트를 지우면 게이트가 조용히 사라집니다. CI에 한 줄씩
추가하면 의도가 드러납니다.

## 권장 순서

**1번 → 3번**이 한 묶음입니다. 검색갭을 수집으로 잇는 순간 평가 케이스 재료가 같이 생기므로,
가장 적은 작업으로 두 개의 고리가 닫힙니다.

**2번**은 작업량이 거의 없고(가시화만), 지금 실제로 멈춰 있는 문제라 바로 효과가 보입니다.

**5번, 6번**은 일관성/방어 성격이라 시간 날 때 하면 됩니다. **4번**은 지금 문제를 일으키지
않으므로 마지막입니다.

## 자동화하면 안 되는 것 (설계 고정)

기존 분석과 동일합니다 — 위키 반영 승인과 실장비 write 승인은 사람 게이트로 남습니다.
HMAC 단일사용 승인이 그 경계이며, 루프로 닫지 않습니다. [SECURITY.md](../SECURITY.md)
